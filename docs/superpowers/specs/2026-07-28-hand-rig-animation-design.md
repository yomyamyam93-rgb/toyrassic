# 손·무기 모션을 애니메이션 클립으로 — 설계

작성 2026-07-28 · 상태: 승인 대기

## 왜 하는가

무기 스윙 자세를 인스펙터 숫자로 맞추고 있다. 스윙 관련 값만 35개고, **전부 플레이를
눌러야만 결과를 볼 수 있다.** 손을 `CreatePrimitive` 로 런타임에 만들기 때문에 에디터에는
손이 존재하지 않고, 그래서 "보면서 맞추는" 도구를 붙일 방법이 없다.

이건 손재주 문제가 아니라 구조 문제다. 사람이 맞출 수 있는 형태가 아니다.

부수적으로, 타격 시점이 `impactDelay = 0.24f` 라는 **짐작한 초 단위 숫자**다. 모션을 바꾸면
매번 다시 어긋난다.

## 결정적 제약 — BlobMotion 이 몸통 트랜스폼을 쓴다

`BlobMotion` 은 플레이어 본인의 트랜스폼을 매 프레임 건드린다.

| 줄 | 하는 일 |
|---|---|
| `BlobMotion.cs:101` | `localScale` 을 **비균등**하게 찌그러뜨림 (스쿼시&스트레치) |
| `BlobMotion.cs:110` | `position.y` — 통통 튐 |
| `BlobMotion.cs:117` | `localRotation` — 기울임 |

**그래서 손을 플레이어의 자식으로 넣으면 손이 같이 찌그러지고 기울어진다.**
현재 코드가 손을 월드 좌표로 계산하는 것은 실수가 아니라 이걸 피하려는 의도적 선택이다.
이 설계는 그 의도를 유지한다.

## 구조

### HandRig — 새 루트 오브젝트 (플레이어의 **형제**)

`HandRig.cs` 가 매 프레임 세 가지만 한다.

| 항목 | 값 | 근거 |
|---|---|---|
| 위치 | 플레이어 위치 | 통통 튐은 따라간다 — 현재 동작과 동일 |
| 회전 | `Quaternion.LookRotation(조준방향, up)` | 지금 코드의 `frame` 을 실제 오브젝트로 꺼낸 것 |
| 크기 | `BlobMotion.baseScale` (0.2239) | **찌그러지기 전** 크기 |

크기를 `baseScale` 로 두면 HandRig 아래의 로컬 공간이 **현재 플레이어 로컬 공간과 단위가
같다.** 기존 값이 1:1로 옮겨오고, `× WorldScale.K` 누락 문제가 이 공간 안에서는 원천적으로
생기지 않는다 (오늘 이 누락으로 여덟 군데가 깨졌다).

`BlobMotion` 에 `baseScale` 읽기 접근자를 추가해야 한다.

### 계층

```
HandRig            ← Animator 붙음. 에디터에 실존
├─ HandL           ← 클립이 구동
│  └─ (새총 거치)
├─ HandR           ← 클립이 구동
│  └─ (도끼·곡갱이·칼 거치)
└─ BowRoot         ← 클립이 구동
   ├─ tool_bow
   ├─ String       ← 코드가 구동 (당김에 연동)
   └─ NockArrow    ← 코드가 구동 (당김에 연동)
```

손과 거치점이 **에디터에 실제로 존재**하는 것이 이 설계의 전부다. 그래야 애니메이션 창이
붙는다.

## 클립 4개

`Carry`(들고다니기) · `Aim`(조준) · `Swing_Vertical`(내려찍기) · `Swing_Horizontal`(가로 긁기)

**무기별 클립은 만들지 않는다.** 방식이 검증되기 전에 늘리면 잘못된 것을 4배로 만드는 셈이다.
무기별 차이는 현재처럼 거치점 오프셋으로 낸다. 검증 후 필요하면 그때 늘린다.

## 코드 경계 — 가장 중요한 규칙

**Animator 가 `HandL`·`HandR`·`BowRoot` 의 위치·회전을 전적으로 소유한다.**
코드는 이 셋의 트랜스폼을 쓰지 않는다. 어기면 코드와 클립이 매 프레임 싸운다.

### 들어내는 것

`PlayerBow.LateUpdate` 의 손·활 배치 코드 (대략 200줄, 796~1017행). 여기에 딸린
인스펙터 값도 함께 제거한다: `handSide`, `handUp`, `swingStartPos/EndPos`,
`hSwingStartPos/EndPos`, `swingStartEuler/EndEuler`, `hSwing*Euler`, `bowAimHandL/R`,
`aimHandL/R`, `carryPos/Euler`, `carrySway`, `toolCarry*`, `swingCurve`, `backswingExtra`.

### 코드에 남는 것

- **시위·화살촉** — 당김 정도에 연속적으로 반응해야 하므로 절차적으로 유지
- **무기 모델 정렬** (`modelEuler`/`modelPos`/`autoRot`) — 모델 임포트 보정이라 별개
- **잔상, 에임 라인, 발사·타격 판정**
- **조준 방향 계산** (`PlayerBow.AimDir`) — HandRig 가 이걸 받아 쓴다

### 코드 → 애니메이터 신호

| 신호 | 형태 | 용도 |
|---|---|---|
| 스윙 시작 | Trigger | `Swing_Vertical` / `Swing_Horizontal` 재생 |
| 가로/세로 | Bool 또는 별도 Trigger | 무기 스타일(`SwingStyle`) 따라 |
| 당김 진행도 | Float (0~1) | `Aim` 클립의 **재생 위치를 직접 지정** |
| 무기 들었나 | Bool | `Carry` ↔ 맨손 |

당김은 클립을 "재생"하는 게 아니라 **코드가 정규화 시간을 직접 넣는다.** 입력에 연속적으로
반응해야 하는 동작을 클립으로 다루는 표준 기법이다.

## 애니메이션 이벤트 — 타격 시점

`impactDelay = 0.24f` 짐작을 없앤다. **도끼가 눈에 보이게 닿는 프레임에 이벤트 마커**를 찍고,
거기서 판정을 부른다. 잔상 켜기/끄기, 파티클, 카메라 흔들림도 같은 방식.

**제약**: 애니메이션 이벤트가 부르는 함수는 `Animator` 와 **같은 GameObject** 위의
컴포넌트에 있어야 한다. 따라서 `HandRig` 에 중계 컴포넌트를 두고 `PlayerGather`·`PlayerBow`
로 넘긴다.

## 마이그레이션

1. `HandRig` 를 만들고 코드가 위치·회전·크기를 구동 — **손은 아직 기존 코드가 배치**
2. 손·활을 `HandRig` 자식으로 옮기고 에디터에 실존시킴 (런타임 생성 제거)
3. 기존 배치 코드가 로컬 좌표를 쓰도록 전환 — **이 시점에 화면 결과가 같아야 한다 (회귀 확인)**
4. 클립 4개 저작, `Animator` 연결
5. 배치 코드 제거, 이벤트로 타격 시점 이관

3번이 안전 지점이다. 여기까지 결과가 같지 않으면 4번으로 가지 않는다.

## 확인 방법 (눈으로)

| # | 확인 |
|---|---|
| 1 | 플레이하면 손이 **지금과 같은 자리**에 있다 (회귀 없음) |
| 2 | 애니메이션 창에서 타임라인을 긁으면 손이 움직인다 |
| 3 | 도끼를 휘두르면 무기가 화면 밖으로 날아가지 않는다 |
| 4 | 타격 판정이 도끼가 **보이게 닿는 순간**에 들어간다 |

## 알려진 비용

- **초기 구성 하루치.** 그 기간 동안은 지금보다 어색해 보인다 — 오늘 맞춰둔 값이 새 공간으로
  옮겨가면서 한 번은 다시 잡아야 한다.
- 오늘 조정한 값 중 손 위치 계열은 **폐기된다.** (크기·잔상·발사점 계열은 유지)

## 범위 밖

- 몸통(BlobMotion) 은 건드리지 않는다. 절차적 스쿼시&스트레치 유지.
- 리깅·블렌더 도입 안 함. 떠 있는 동그란 손 스타일 유지가 전제.
- 무기별 전용 클립은 이번에 만들지 않는다.
- 플레이어 GameObject 에 컴포넌트 16개가 붙어 있는 문제는 별건으로 둔다.
